### One model, one record

`fhcost/` is the only implementation. Everything else consumes `RESULTS.json`:
the explorer's constants, the headline prose, and the model fingerprint stamped
on the figure, the slide, `crossovers.md` and the explorer's header. **If two
artefacts show different model ids they came from different models and must not
be compared.**

The explorer is still JavaScript, so it is still a second implementation of the
*functions* — but it is not a second set of assumptions, and it is not trusted on
faith. It recomputes eight configurations' worth of intermediates (steps, signal,
gate counts, shot counts, code distance, workspace, factory choice, footprint,
per-shot time) against the Python answers on every page load and prints the
verdict in its own header. `check_parity.py` reads that verdict back out of a
headless Chrome. A 10⁻⁷ nudge to one line of the port trips 209 of those probes,
so it is not a soft check.

Nothing here runs a simulation: the classical entries are closed-form memory and
flop counts, not state vectors or tensors. If the models are ever validated
against a real small-lattice ED run, note that m = 16 already needs ~2.6 GB per
state vector and m = 18 needs ~38 GB — run that on `lenore_remote` (port 60022),
not on this machine, and put a hard memory guard on it.
